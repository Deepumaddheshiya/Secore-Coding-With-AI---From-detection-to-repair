## 1. Executive Summary & Research Objectives

While numerous prior studies have scrutinized the security and functional correctness of code produced by generative Large Language Models (LLMs), nearly all past research relied upon synthetic, lab-generated prompts or simulated developer interactions. This paper bridges that critical gap by empirically evaluating:
1. **Real-world code snippets** created during authentic human-AI interactions curated in the **DevGPT** dataset (snapshots October 2023 and May 2024).
2. **Multi-scanner static application security testing (SAST)** on C-family languages (C, C++, C#).
3. **Longitudinal progression** of LLM security capabilities across two distinct milestones:
   - **October 2024:** GPT-4o (baseline evaluation).
   - **September 2025:** Modern frontier models: GPT-4.1, GPT-5, and Claude Opus 4.1.
4. **Vulnerability Detection and Automated Remediation (Repair)** effectiveness across both human-written developer prompts and LLM-generated code answers.

## 2. Core Research Questions (RQs) and Key Findings

### RQ1: How secure is the code generated by GPT in the DevGPT dataset?
- **Scope & Method:** Evaluated 2,315 source files in C, C++, and C# extracted from DevGPT (version 10, snapshots `snapshot_20231012` and `snapshot_20240514`) using four static security scanners: Flawfinder, Snyk, Semgrep, and Cppcheck.
- **Finding:** Scanners flagged potential issues in 114 files (141 raw scanner detections). Comprehensive manual inspection by software security experts confirmed **56 real security vulnerabilities across 48 files**.
- **Conclusion:** Real-world developer interactions with GPT frequently incorporate or generate insecure code snippets requiring rigorous verification.

### RQ2: How effective are LLMs in detecting and correcting security issues when explicitly asked to do so?
- **October 2024 (GPT-4o):** Detected only 18 out of 32 confirmed issues (56.25%) and resolved 17 out of 32 (53.125%).
- **September 2025 (Frontier Models):**
  - **GPT-4.1:** Detected 46/56 (82.14%), Fixed 42/56 (75.00%).
  - **GPT-5:** Detected 44/56 (78.57%), Fixed 44/56 (78.57%).
  - **Claude Opus 4.1:** Detected 45/56 (80.36%), Fixed 43/56 (76.79%).
- **Finding:** Capabilities advanced markedly in one year from ~53–56% to ~75–82%. However, models frequently hallucinate non-existent CWEs with high subjective confidence, over-correct safe code (sycophancy), or fail to recognize complex memory or race condition bugs.

### RQ3: Do developers provide more vulnerable code, or does GPT generate more insecure code during interactions?
- **October 2024:** 10 vulnerabilities originated from developer prompts, while 22 vulnerabilities were introduced in GPT-4o responses.
- **September 2025:** 25 vulnerabilities originated from user prompts (44.64%), while 31 vulnerabilities originated from GPT responses (55.36%).
- **Finding:** LLMs and human developers introduce vulnerabilities at comparable rates in conversational workflows. LLMs perform slightly better at detecting/repairing human-written code than inspecting their own generated output.

## 5. Security Vulnerability & CWE Classifications

Across the 56 confirmed vulnerabilities, **66 CWE assignments** were identified (some issues involve dual CWEs such as buffer overflows with input validation):
- **Most Prevalent:** CWE-20 (Improper Input Validation, 16 instances) and CWE-120 (Classic Buffer Overflow, 11 instances), jointly accounting for 40.9% of all assignments.
- **Top 25 CWEs:** 6 classifications reside on the 2024 CWE Top 25 Most Dangerous Software Weaknesses list (CWE-20, CWE-22, CWE-78, CWE-119, CWE-190).
- **Concurrency & State:** CWE-362 (Race Condition, 7 instances).
- **Other Notable:** CWE-327/328 (Broken Cryptography/Hash), CWE-665 (Improper Initialization), CWE-401 (Memory Leak), CWE-78 (OS Command Injection).

## 6. Key Qualitative Observations

1. **Sycophancy & Over-correction:** When instructed to look for vulnerabilities, LLMs frequently modify benign code, manufacturing non-existent security rationales to satisfy user prompts.
2. **Hallucinated CWE Identifiers:** LLMs frequently invent CWE classifications or apply broad categories (e.g., calling OS command injection CWE-77 instead of specific CWE-78).
3. **Unsupervised Risks:** Because LLMs output incorrect assertions with extreme linguistic confidence, unsupervised automated repair poses severe regression risks in production software.
